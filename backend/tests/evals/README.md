# Evals

Two things live here, and they are deliberately separate directories:

- **`data/`** — the golden set, generated by [deepeval](https://deepeval.com)'s synthesizer and
  committed. One entry per question, with the answer we expect and the corpus text it must be
  grounded in.
- **`retriever/`** — an eval suite that scores retrieval against that golden set. See
  [Retriever evals](#retriever-evals).

```
tests/evals/
├── README.md
├── conftest.py          # truststore + OPENAI_API_KEY, applies to every suite here
├── data/
│   └── goldens.json     # the dataset
└── retriever/
    ├── adapters.py      # dense / sparse / hybrid -> retrieved chunk texts
    ├── metrics.py       # the shared judge and thresholds
    ├── test_dense.py
    ├── test_sparse.py
    └── test_hybrid.py
```

`goldens.json` is committed on purpose. Regenerating costs real OpenAI tokens, and a dataset
that changes should show up as a reviewable diff rather than appearing out of nowhere on
someone's machine.

## Schema

```jsonc
{
  "input": "My X200 stopped charging after three months...",   // the question to send the app
  "expected_output": "Covered under warranty §2.3 — free replacement...",
  "context": ["Covered for 24 months from delivery..."],       // the chunk it was written from
  "source_file": "warranty-policy.md",                         // ground truth: what must be retrieved
  "additional_metadata": {
    "corpus": "policy",                 // "policy" | "case"
    "source_ref": "warranty-policy.md", // policy filename, or case id ("C-1001")
    "expected_department": "warranty",  // null = company-wide policy, not "unknown"
    "title": "Product Warranty Policy",
    "context_quality": 0.83,            // deepeval's own critic scores, carried through
    "synthetic_input_quality": 0.91,
    "evolutions": ["Reasoning"]
  }
}
```

`expected_department` and `source_ref` are what make retrieval measurable: routing accuracy is
"did the classifier pick `expected_department`", retrieval hit rate is "was `source_ref` among the
chunks we retrieved". Both are free to compute — no LLM judge needed.

## Regenerating

Two commands. Only the first costs money.

```bash
cd backend

# The generation step. A few minutes, real OpenAI spend.
# --dry-run materialises the corpus and prints it without generating anything.
uv run cms-evalset build

# Is each golden's own source actually retrievable? Free, needs Qdrant.
uv run cms-evalset verify
```

That is the whole flow. `build` is deepeval's documented document path —
`Synthesizer().generate_goldens_from_docs(document_paths=[...])` — wrapped in the two things it
cannot do for itself: point it at a corpus it can read, and join its `source_file` back to the
department and title the evals need.

### Three things worth knowing

- **`chromadb` is required.** deepeval's document path uses it for chunk storage during context
  construction. It is in the `dev` dependency group; `uv sync` is enough.
- **The seed corpus is materialised, not read in place.** `cases.json` is not a format deepeval
  can load, and policy frontmatter would be chunked as content — so `cms.evals.corpus` writes 34
  frontmatter-stripped policies and 20 case files into a temp directory on every run. That is
  also what lets the whole dataset come out of a *single* `generate_goldens_from_docs` call.
- **Rate limits.** `--max-concurrent` is pinned to 3 and the generator to `gpt-4.1-mini`, because
  this account caps `gpt-4.1` at 30k TPM and nothing is written to disk until the run finishes.

## Why the document path

The previous build used `--method contexts`, hand-building contexts from the project's own
`chunk_policy` output. That bought chunk fidelity and cost far more than it was worth:

1. **`--method contexts` has no `source_files` parameter.** A generated golden came back with
   `source_file: null` and no way home, which forced a `POLICY warranty-policy.md (warranty) — …`
   header to be smuggled into the context text and parsed back out with a regex afterwards. The
   generator read that header too, and wrote self-answering questions from it. The document path
   fills in `source_file` itself, so the header, the regex and the whole `annotate` step are gone.
2. **It skipped deepeval's context critic.** `context_quality_threshold` runs inside
   `ContextGenerator`, which only the document path uses. Hand-built contexts were never quality
   gated.
3. **It needed three commands and three files.** `export-contexts` → `deepeval generate` →
   `annotate`, with `contexts.json` and `generated.json` as intermediates.

The chunk-fidelity argument does not survive contact with the metrics: `ContextualPrecision`,
`ContextualRecall` and `ContextualRelevancy` judge *semantic* support, not string identity, and
`chunk_size=800 / chunk_overlap=100` puts deepeval's splitter on the same budget as `chunk_policy`
anyway. The region is what matters; the exact cut is not.

## What `build` changes from deepeval's defaults, and why

Nothing about the prompts — there is no `StylingConfig`, no `--scenario`, no `--input-format`. The
previous build asked for "order numbers ... and Rupee amounts where relevant" and got exactly
that: "order 12345" and "Rs. 15,000", invented facts appearing nowhere in the corpus, which no
retrieval could ever support. Ungrounded goldens were caused by the instruction to embellish, so
there is no instruction. Left unstyled, the generator has nothing to work from but its chunk.

Only `ContextConstructionConfig` is customised, and only where a default is wrong here:

| Setting | Default | Here | Why |
| --- | --- | --- | --- |
| `max_context_length` | 3 | **1** | A three-chunk context can only be recalled if the retriever returns all three. This failed 26 of the previous 40 goldens on structure alone, whatever the retriever did. |
| `max_contexts_per_document` | 3 | **1** | One golden per seed document: all 54 covered exactly once, no sampling needed. |
| `chunk_size` / `chunk_overlap` | 1024 / 0 | **800 / 100** | `chunk_policy`'s budget, so a context is the size of a chunk the retriever indexes. |
| `encoding` | autodetect | **`utf-8`** | Not optional on Windows. deepeval hands this to `TextLoader`, where `None` means the platform codepage (cp1252) — the corpus is UTF-8 and full of ₹ and §, so the default silently yields `â‚¹8,000` and `Â§2.3` in every context. |

## Reviewing a run

Generated goldens are not automatically good. Before committing a regenerated dataset:

```bash
# Size, coverage, and the one-chunk invariant
uv run python -c "import json,collections; g=json.load(open('tests/evals/data/goldens.json',encoding='utf-8')); print(len(g),'goldens'); print('chunks per context:',collections.Counter(len(x['context']) for x in g)); print(collections.Counter(x['additional_metadata']['corpus'] for x in g)); print(sorted({str(x['additional_metadata']['expected_department']) for x in g}))"

# Nothing invented: no order number should appear that is not in the corpus
uv run python -c "import json,re; g=json.load(open('tests/evals/data/goldens.json',encoding='utf-8')); [print(x['source_file'],'::',x['input'][:90]) for x in g if re.search(r'[Oo]rder\s*#?\s*\d{4,}',x['input']+(x['expected_output'] or ''))]"

# Is the source actually retrievable? This is the point of the dataset.
uv run cms-evalset verify
```

Then read about five inputs by hand. Reject the run if they read as corpus trivia ("what does
§2.3 say?") rather than questions worth asking — it is much cheaper to catch here than after a
metric is built on top of it.

`cms-evalset verify` exits non-zero if any golden's own source is unreachable. Such a golden is a
broken ruler: the retriever evals will score it as a failure however good retrieval is.

## The committed run

Generated 2026-08-21 with `gpt-4.1-mini` at `--max-concurrent 3`. Cost **$0.1026**, ~5 minutes.

- **54 goldens** — 34 policy, 20 case
- **54 distinct `source_ref`s** — every seed document represented exactly once
- **1 context chunk each**, all 54 — the invariant the retriever evals depend on
- **13 department strata** — all 12 departments, plus company-wide policies
- **0** goldens with an unresolved source or a missing `expected_output`
- **0** invented identifiers: the three order/batch numbers that appear (`#9021`, `#6555`,
  `#MB-2291`) are all real text from `cases.json`
- `cms-evalset verify`: **54/54** sources retrievable in the top-10, mean rank 4.8, worst 8

For contrast, the previous contexts-based run produced 40 goldens of which 26 carried three-chunk
contexts, 5 cited invented order numbers and 14 invented Rupee amounts.

## Retriever evals

`retriever/` scores retrieval — and only retrieval — against the golden set in `data/`. There is
no `generate` node in the graph yet, so retrieval is the only stage that can be evaluated
end-to-end today, and none of the three metrics need an `actual_output`:

| Metric                      | What it asks                                                    | Threshold |
| --------------------------- | --------------------------------------------------------------- | --------- |
| `ContextualPrecisionMetric` | Are the relevant chunks ranked *above* the irrelevant ones?     | 0.7       |
| `ContextualRecallMetric`    | Does the retrieved set cover everything `expected_output` needs? | 0.7       |
| `ContextualRelevancyMetric` | How much of what came back is actually on topic?                | 0.5       |

Relevancy sits lower on purpose: it penalises every irrelevant *sentence* inside an
otherwise-correct chunk, and `chunk_policy` cuts policies at 800 tokens. A 0.7 bar there would
fail retrievals that are in fact correct.

### Three files, three retrievers

One file per retriever, because the comparison *is* the result:

- `test_dense.py` — the semantic leg alone (OpenAI embeddings, cosine)
- `test_sparse.py` — the lexical leg alone (local BM25, exact terms)
- `test_hybrid.py` — what production uses: both legs, both collections, RRF-fused

All three are driven by the raw `golden.input`. No query rewriting, no department filter — the
scores describe the retriever and nothing upstream of it. All three return the same 10-chunk budget
(6 cases + 4 policies), which is what makes the numbers comparable. If hybrid is not beating
`max(dense, sparse)` on recall, `RRF_K` and `FETCH_K` in `hybrid_retriever.py` are the first knobs.

### Running them

Qdrant must be up and both collections populated — `uv run cms-retrieve "warranty claim" --json`
should return non-empty `cases` *and* `policies` first. Run `uv run cms-evalset verify` before
spending anything here; it is free and catches the goldens these runs cannot pass.

```bash
cd backend
uv run cms-deepeval test run tests/evals/retriever/test_dense.py  --num-processes 4 --ignore-errors --identifier retriever-dense-round-1
uv run cms-deepeval test run tests/evals/retriever/test_sparse.py --num-processes 4 --ignore-errors --identifier retriever-sparse-round-1
uv run cms-deepeval test run tests/evals/retriever/test_hybrid.py --num-processes 4 --ignore-errors --identifier retriever-hybrid-round-1
```

Three things worth knowing before you start:

- **Budget and time scale with the dataset.** 3 LLM-judged metrics per golden, measured at
  ~$0.042 per golden on `gpt-5.4-mini`. Cost is printed at the end of every run.
- **`pytest` alone will not run these.** `norecursedirs` in `pyproject.toml` keeps the whole
  `evals/` tree out of the ordinary suite, so nobody spends money by running `uv run pytest`.
  Explicit paths — like the commands above — still collect.
- **Keep `--num-processes` around 4.** This account is capped at 30k TPM and each judge call
  carries ten chunks of policy text.

### The judge

`gpt-5.4-mini`, pinned in `retriever/metrics.py`. deepeval has that id in its model registry, which
buys three things a newer or dated id would not: it forces `temperature=1` instead of the `0.0` the
gpt-5 reasoning endpoint rejects, it uses native structured outputs for the verdicts rather than
reparsing JSON, and its prices are registered so the cost line at the end of a run is real.

### `cms-deepeval`, not `deepeval`

The plain CLI is a separate process, so it never imports `cms.config` and never gets the truststore
injection. Behind this machine's TLS-intercepting proxy every OpenAI call then dies with
`CERTIFICATE_VERIFY_FAILED`. `cms-deepeval` is deepeval's own Typer app with that bootstrap applied
and `OPENAI_API_KEY` loaded from `.env` — same flags, same help, same exit codes. `cms-evalset`
applies the same bootstrap in-process.
